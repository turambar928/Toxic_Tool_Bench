\section{Discussion and Limitations}
\label{sec:discussion}

ToxicBench targets a narrow but important reliability question: whether tool-using data agents can distinguish a successful tool call from a trustworthy observation. This focus has several implications.

First, not every surprising tool output is wrong. Real datasets contain outliers, schema mistakes, and counterintuitive relationships. A robust agent should not reject observations merely because they are unexpected; it should validate them. For this reason, our metrics distinguish anomaly detection, validation, and recovery.

Second, benchmark poisoning should not be unrealistically obvious. If every poisoned observation violates a simple invariant, the benchmark measures only basic sanity checking. We therefore include multiple severity levels and semantic poison cases where the discrepancy requires cross-checking across tools or data sources. The current semantic/schema suite includes biased retrieval evidence and has been run across the same three-model set as the numerical cross-model experiments for the completed adapters. It is still small enough that larger task families and tighter confidence intervals are needed before making fine-grained model-level claims.

Third, poisoning boundaries differ across frameworks. LangGraph, smolagents, and AutoGen expose relatively direct tool-observation boundaries. PandasAI is currently poisoned at a coarser chat-result boundary, and DA-Agent observations may include execution traces. These are realistic end-to-end surfaces, but they are not identical instrumentation points. We therefore report adapter-specific limitations rather than treating every number as a pure model comparison.

Fourth, Guarded Verification assumes that an independent verification path is available and not simultaneously corrupted. In the defense ablation, the proxy corrupts the first matching route and the guard can recover by re-reading raw rows, recomputing an aggregate, or checking source evidence. This models pipeline bugs, stale summaries, biased retrieval snippets, or single-route proxy compromise. It does not solve settings where the underlying database itself is corrupted, where all redundant APIs share the same poisoned cache, or where an adaptive adversary observes and poisons both primary and verification routes. We therefore treat poison-once as a controlled lower bound on the difficulty of silent poisoning, not as a universal threat model. Stronger baselines such as multi-route ensembling, randomized cross-checks, provenance validation, and selective verification policies are natural next comparisons.

Fifth, Guarded Verification increases tool-use and routing overhead because it asks the agent to write expectations and perform validation. In the expanded LangGraph ablation, base toxic runs average about two tool events per environment, while full guarded toxic runs average roughly four to five tool events depending on the suite. Median wall-clock latency rises from about 7.3 seconds to 21.3 seconds on LangGraph, and AutoGen replication shows a similar 25--27 second operating range with four tool events on average. We report a cost--robustness table using both tool events and wall-clock latency, plus a compact latency distribution table in the appendix. We do not report monetary cost because the API gateways used here do not expose reliable per-call billing across all model endpoints. The light variant keeps observed BCR at zero and remains close to full guard in aggregate, but individual qualitative cases still show under-recovery when verification needs more turns. Future work should learn when to activate full verification only for high-risk observations, rather than always paying the full verification cost.

Finally, the benchmark should be evaluated across more open and closed models, different data-agent architectures, larger databases, multi-table joins, and notebook-like workflows where recomputation requires more planning. The main claim is not that a particular model fails on an isolated case, but that blind compliance is a measurable and recurring behavior under controlled silent tool unreliability. The current experiments establish this behavior and show that structured guarded verification can reduce it; the next step is broader task scaling, overhead-aware guard activation, and stronger uncertainty estimates for final answers.

Selective verification remains open. Our abstain, randomized, and selective baselines show that cheaper policies can reduce blind compliance on some semantic/schema tasks, but they are brittle on harder numerical cases and do not yet provide a learned trigger. We therefore view them as stress tests for the cost--robustness tradeoff, not as a replacement for the full guard. A future version should report trigger-level precision--recall or AUC for predicting when verification is needed, then compare the resulting policy against always-on verification at matched latency or tool-event budgets.
