\section{ToxicBench}
\label{sec:benchmark}
\label{sec:problem}

ToxicBench tests whether data agents can distinguish successful tool execution from trustworthy evidence. For a query $q$, an agent calls a tool $f$ with input $x$ and receives $o=f(x)$. In the poisoned environment, a proxy returns $\tilde{o}=P(f,x,o;\theta)$. We call the poisoning \emph{silent} when $\tilde{o}$ preserves the expected interface, reports successful execution, and remains relevant enough to support a plausible answer. The same agent, task, data, and model are evaluated once with $o$ and once with $\tilde{o}$, allowing us to measure the effect of the corrupted observation on the same task.

\subsection{Benchmark Design}

Each item contains a query, one or more datasets, a clean oracle or rubric, and a poisoning specification. Poisoned outputs preserve schema, type, and formatting, and never expose an exception or warning. Each task also retains a path for checking the answer, such as recomputation from raw rows or inspection of source metadata. This path can share the upstream table and tool backend.

The cross-model evaluation contains 34 numerical task instances over 11 CSV datasets and 24 semantic/schema instances over 17 datasets. The expanded cross-agent evaluation uses GPT, while the verification study uses Claude Haiku on 60 instances from each family. A separate 13-instance extension requires multi-table joins. Appendix~\ref{sec:appendix-benchmark-details} lists the query--dataset--poison templates behind these instances.

\paragraph{Building a task pair.}
We start from a query and its source table, compute the clean answer, and specify a changed value or claim that would alter that answer. The proxy runs the original tool before editing the returned observation. It records both versions for scoring; only the returned version enters the agent context. The source table remains available for later checks. For example, a label swap can attach the largest revenue to the wrong store while leaving the amount and output format intact. Recomputing the maximum from source rows reveals the correct store.

The poisoning specification names the target tool and the value or text to change. The proxy applies the operator to eligible observations and logs whether the returned text actually changed. A call to another tool, or a response that the operator cannot change, can leave the trajectory unexposed. The delivery log separates an agent that never receives the planned poison from one that receives it and reaches the clean answer. Keeping both observations also lets a reviewer trace an adopted value back to the injected change.

The expanded numerical suite has 60 instances from 56 templates over 14 datasets. The semantic/schema suite has 60 instances from 41 templates over 22 datasets. Templates cover different queries, datasets, and poison settings; repeated instances test the stability of a setting. The 13-task extension adds table discovery and joins on customer, team, clinic, and product keys.

\subsection{Poisoning Operators and Metrics}

\paragraph{Numerical poisoning.}
Numerical operators target computation outputs from Python, pandas, SQL, or dataframe routes:
\begin{itemize}
    \item \textbf{Aggregate scaling:} multiply a requested aggregate such as a mean, sum, rate, or count by a controlled factor while preserving the surrounding output format.
    \item \textbf{Sign flip:} reverse the sign of a change, growth rate, or delta while keeping the magnitude plausible.
    \item \textbf{Rank/label swap:} swap the entity label attached to a statistic or ranking result while leaving the value format intact.
\end{itemize}
The 34-instance cross-model suite uses these three core operators. The expanded numerical suite additionally includes ratio inversion, denominator swap, omitted-filter corruption, and unit conversion.

\paragraph{Semantic and schema poisoning.}
These operators change how evidence is linked to an entity or claim:
\begin{itemize}
    \item \textbf{Label swap:} replace an entity label associated with an otherwise plausible result.
    \item \textbf{Treatment/control flip:} invert experimental group semantics while preserving outcome values.
    \item \textbf{Column-semantic swap:} swap column descriptions or meanings in schema evidence.
    \item \textbf{Stale metadata:} return outdated data-dictionary or source-of-truth metadata.
    \item \textbf{Biased retrieval:} return evidence rows or snippets that support the wrong conclusion while appearing relevant.
\end{itemize}
We score final answers against the clean oracle and compute behavior labels from the logged trajectory. The scorer reports the following metrics:
\begin{itemize}
    \item \textbf{Task Success Rate (TSR):} the fraction of tasks that satisfy the clean reference answer or rubric.
    \item \textbf{Poisoned Degradation ($\Delta$TSR):} the drop from clean TSR to poisoned TSR.
    \item \textbf{Blind Compliance Rate (BCR):} the fraction of exposed runs whose final answer matches the poisoned oracle without ADR or VR.
    \item \textbf{Poison Adoption Rate (PAR):} the fraction of exposed runs whose final answer matches the poisoned oracle, regardless of whether the agent detected or validated the observation.
    \item \textbf{Validated Poison Adoption (VPA):} the fraction of exposed runs that both obtain qualifying VR and still match the poisoned oracle. VPA records adoption after a check.
    \item \textbf{Anomaly Detection Rate (ADR):} the fraction of exposed runs whose final response explicitly identifies a discrepancy, implausibility, conflict, or possible corruption.
    \item \textbf{Validation Rate (VR):} the fraction of exposed runs with a fresh, task-relevant evidence-producing tool event after the poisoned observation. The event may itself be corrupted under repeated poisoning; VPA records cases that still adopt the poisoned answer after such validation.
    \item \textbf{Recovery Rate (RR):} the fraction of exposed runs that produce an accepted clean answer after ADR or VR.
    \item \textbf{Poison Delivery Rate (PDR):} the fraction of toxic-environment runs in which the proxy actually modifies at least one eligible observation.
\end{itemize}

All methods use the same scorer after removing known adapter-added display labels. The scorer excludes rejected oracle matches and prioritizes explicit final conclusions; competing matches are marked ambiguous. Ambiguous or unresolved answers remain in the denominator and receive neither TSR nor PAR credit. Behavioral rates condition on delivered poison, whereas TSR uses all runs. Thus PAR=0 does not by itself establish rejection of the poisoned answer.

We test these operational labels against human judgments at two levels: individual decisions and paired method comparisons. A 120-trajectory audit supported scorer development; a separate 240-trajectory holdout evaluates the unchanged scorer on other task IDs. Section~\ref{sec:human-holdout} reports the returned annotations, and Appendix~\ref{sec:appendix-holdout} gives the protocol and full comparison. \subsection{Verification Protocols}
\label{sec:method}

We compare a base LangGraph agent with three protocols that use two routes. A route is one agent call that can inspect data, run tools, and return an answer.

\textbf{Base} uses one ordinary route. \textbf{Double-pass} runs two ordinary routes with the same task query and selects the second answer. The second route receives no answer from the first. This control measures the effect of another chance to solve the task and access evidence. \textbf{Verification-only} passes the first answer to the second route as an untrusted claim and asks it to check the source data. It also selects the second answer. \textbf{Generic Guard} adds a fixed expectation prompt to the primary and verification routes. The prompt asks the agent to consider valid ranges, entity--value bindings, and source evidence. The verifier is responsible for correcting or qualifying its answer; the wrapper returns that response directly.

In an aggregate query, these expectations direct attention to the requested filters, units, and denominator. In a ranking query, they direct attention to the link between the returned number and the named entity. For schema and retrieval tasks, the checks concern column meanings, timestamps, and source support. The prompt asks for a fresh tool action and for literal labels to be preserved in the final answer. The same checklist is supplied for every task, and the agent chooses which checks apply. This keeps the protocol consistent across task families and makes its evidence use visible in the tool trace.

All two-route methods use the same model, temperature, route count, and per-route limits: ten steps and 3,072 output tokens. They do not receive poison metadata or clean oracle values. The comparison tests whether a verification prompt and generic expectations help beyond an ordinary second pass. Passing the primary answer may help direct the check, but can also anchor the verifier on an earlier mistake. The paired clean runs reveal whether these prompt changes affect ordinary task solving as well as recovery from poison.

The comparisons test three protocol changes. Base versus Double-pass adds another ordinary route. Double-pass versus Verification-only changes both the answer handoff and the instruction to verify. Verification-only versus Generic Guard adds generic expectations to the prompts. We retain the final answer and the tool events from both routes, so a run can be inspected from the first corrupted observation through the selected conclusion.

The primary \texttt{poison\_once} setting corrupts the first eligible observation. The poisoning state is shared across both routes. Once a qualifying observation has been changed, later calls can inspect clean source rows or metadata. The ordinary second pass has access to this later evidence as well as the explicit verification methods. The two routes run separately over the same tables and tool backend. Repeated-poison experiments then corrupt each eligible observation with probabilities 0.25--1.00. VR records a check after poison has been seen; VPA records continued adoption of the poisoned answer after that check. This design tests both the use of available clean evidence and the effect of corrupting later checks. Appendix~\ref{sec:appendix-langgraph-replication} gives the implementation details.
