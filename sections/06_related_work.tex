\section{Related Work}
\label{sec:related}

\paragraph{Tool-augmented language agents.}
Tool-augmented language models use external APIs, retrieval systems, program interpreters, and environment actions to solve tasks beyond ordinary text generation. Prior work studies how models learn to call tools, interleave reasoning and acting, or use programs as intermediate computation \citep{schick2023toolformer,yao2023react,gao2023pal}. Tool-use benchmarks and API corpora such as ToolLLM/ToolBench, API-Bank, and Gorilla evaluate whether models can select tools, construct valid arguments, and complete tool-mediated tasks \citep{qin2023toolllm,li2023apibank,patil2024gorilla}. \benchmarkname{} studies a complementary dimension: after a tool call succeeds and returns a syntactically valid observation, can the agent decide whether that observation deserves trust?

\paragraph{Agent reliability and error recovery.}
General agent benchmarks evaluate long-horizon planning, interaction with web or software environments, and recovery from invalid actions or incomplete context \citep{liu2023agentbench,zhou2023webarena}. These settings expose important failures in task decomposition, state tracking, and environment interaction. Silent tool poisoning differs because the failure is not an explicit invalid action, exception, or missing observation. The agent receives a normal-looking result at the expected interface, so the challenge is semantic skepticism toward plausible evidence rather than syntactic recovery from an error signal.

\paragraph{Prompt injection and data poisoning.}
Data-embedded instruction risks in \benchmarkname{} are related to prompt injection and indirect prompt injection, where untrusted retrieved or tool-provided content can influence downstream model behavior \citep{perez2022ignore,greshake2023indirect}. Our attack surface is broader than explicit instruction strings: poisoned observations may be corrupted aggregates, swapped labels, stale metadata, or biased retrieved evidence. The desired behavior is therefore not merely refusal. A robust data agent should continue the analysis while treating tool observations as evidence to validate rather than commands or facts to copy.

\paragraph{Data quality and schema reliability.}
Data-analysis agents depend on schemas, data dictionaries, documentation, and retrieved evidence to decide which columns and rows are relevant. Data validation and data-quality systems check constraints such as types, missing values, distribution shifts, and schema expectations before data enters downstream workflows \citep{schelter2018automating,breck2019data}. \benchmarkname{} moves this reliability question into the agent loop. Instead of only asking whether a dataset violates a declared constraint, we ask whether an agent over-trusts plausible but wrong metadata, such as swapped column semantics, stale source-of-truth fields, or inverted treatment labels.

\paragraph{Uncertainty and self-verification.}
Self-checking and verification methods ask models to critique, revise, or validate their own outputs \citep{shinn2023reflexion,madaan2023selfrefine}. \methodname{} applies this idea at the tool-observation boundary. The guard forms expectations before tool use, checks returned observations against those expectations, and performs independent validation before finalization. This framing separates clean task competence from trust calibration: an agent can know how to solve the data-analysis task and still fail if it treats every successful tool observation as ground truth.
