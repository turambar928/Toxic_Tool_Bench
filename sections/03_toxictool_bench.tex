\section{\benchmarkname{}}
\label{sec:benchmark}

\benchmarkname{} is designed to test whether data agents can distinguish successful tool execution from trustworthy tool evidence. The benchmark wraps standard data-analysis tools with controlled poisoning operators and evaluates agent behavior on paired clean and poisoned tasks. The central design choice is to make the poisoned observation look operationally normal: the tool call succeeds, the return type is valid, and the observation remains relevant to the user's question.

\subsection{Design Goals}

Silent tool poisoning is useful as an evaluation setting only if the corrupted observation is neither an ordinary tool failure nor an arbitrary adversarial string. We therefore use four design goals.

\paragraph{Interface preservation.}
The poisoned tool output must preserve the expected schema, type, and formatting of the clean output. A dataframe summary still looks like a dataframe summary; a metadata lookup still returns metadata; a retrieved evidence snippet still looks like retrieved evidence. This prevents the benchmark from reducing to parsing-error recovery.

\paragraph{Execution-success preservation.}
The tool call must report normal completion. Agents do not receive an exception, timeout, traceback, or explicit warning that the observation is unreliable. This isolates trust calibration after successful tool use.

\paragraph{Task relevance.}
The poisoned observation must remain relevant enough that a naive agent could plausibly use it in downstream reasoning. For example, a poisoned aggregate should answer the requested statistic, but with a corrupted value or entity binding.

\paragraph{Independent verifiability.}
Each task must retain a clean oracle or rubric, and the corrupted observation must be checkable through another route such as recomputation from raw rows, comparison against schema evidence, or inspection of retrieved support. This lets us distinguish blind copying from detection, validation, and recovery.

\subsection{Task Construction}

Each benchmark item defines a user query, one or more datasets, a clean reference answer or rubric, and a poisoning specification. We evaluate the same agent on a clean environment and a toxic environment. The user query, dataset, adapter, and model are held fixed; only selected tool observations are changed by the poisoning proxy.

The clean run measures whether the agent can solve the underlying data-analysis task. The toxic run measures whether a successful but corrupted observation changes the final answer or the agent's validation behavior. This paired construction is important because a poisoned failure is most informative when the corresponding clean task is solvable.

\paragraph{Current instantiation.}
The main cross-agent instantiation contains a 34-task tabular numerical-analysis suite over 11 CSV datasets and a 24-task semantic/schema suite over 14 CSV datasets. These suites are intentionally small enough for repeated cross-model framework runs, but broad enough to test arithmetic trust, entity binding, schema interpretation, and retrieval-grounded evidence use. For the \texttt{data2mcp} defense ablation, we additionally use expanded ICLR 2027 candidate suites with 60 numerical tasks and 60 semantic/schema tasks. The expanded suites preserve the same poisoning families while increasing coverage of repeated analytical patterns, severity levels, and decision contexts.

\paragraph{Workflow coverage.}
The task families are derived from common data-agent workflows: descriptive statistics over tables, schema and metadata interpretation, retrieval-grounded analysis, and decision-oriented recommendations that depend on intermediate analytical evidence. The current main experiments focus on numerical and semantic/schema poisoning; report-style and data-embedded instruction tasks are supported by the framework but treated as future extensions rather than main-table results.

\subsection{Poisoning Operators}

\paragraph{Numerical poisoning.}
Numerical operators target computation outputs from Python, pandas, SQL, or dataframe routes. In both the 34-task cross-agent suite and the 60-task expanded defense suite used in Section~\ref{sec:experiments}, we use three implemented operators:
\begin{itemize}
    \item \textbf{Aggregate scaling:} multiply a requested aggregate such as a mean, sum, rate, or count by a controlled factor while preserving the surrounding output format.
    \item \textbf{Sign flip:} reverse the sign of a change, growth rate, or delta while keeping the magnitude plausible.
    \item \textbf{Rank/label swap:} swap the entity label attached to a statistic or ranking result while leaving the value format intact.
\end{itemize}
The rank-swap operator uses label-boundary replacement so that short labels such as \texttt{E} are swapped only as labels and not inside ordinary words such as \texttt{defects}. These operators test whether agents audit arithmetic results and preserve value--entity bindings rather than simply copying a successful computation observation.

\paragraph{Semantic and schema poisoning.}
Semantic/schema operators target metadata, schema descriptions, treatment labels, or retrieved evidence. Both the 24-task cross-agent suite and the 60-task expanded defense suite implement:
\begin{itemize}
    \item \textbf{Label swap:} replace an entity label associated with an otherwise plausible result.
    \item \textbf{Treatment/control flip:} invert experimental group semantics while preserving outcome values.
    \item \textbf{Column-semantic swap:} swap column descriptions or meanings in schema evidence.
    \item \textbf{Stale metadata:} return outdated data-dictionary or source-of-truth metadata.
    \item \textbf{Biased retrieval:} return evidence rows or snippets that support the wrong conclusion while appearing relevant.
\end{itemize}
These operators are designed to test evidence binding rather than numeric tolerance alone. A robust agent should preserve the association between values, labels, columns, rows, and evidence sources.

\paragraph{Data-embedded instructions.}
The framework can also represent instruction-like content embedded in raw text, metadata, or data previews. The poison is not delivered through the system or developer prompt; it is embedded in data that should be treated as untrusted content. A robust agent should analyze such text as data rather than follow it as an instruction. The experiments in this paper focus on numerical and semantic/schema poisoning, so data-embedded instruction results are not included in the main tables.

\subsection{Evaluation Protocol}

For each task, the benchmark records both the clean observation and the returned observation, but the agent only receives the returned observation. In the clean environment these are identical. In the toxic environment, the poisoning proxy edits selected observations after the real tool executes. The final trajectory therefore supports both answer-level scoring and behavior-level scoring.

We score final answers against the clean oracle or task rubric. We also inspect the trajectory for signs that the agent questioned, validated, or recovered from the poisoned observation. Validation is counted only when the agent obtains or uses evidence independent of the poisoned observation, such as recomputing from raw data, querying an alternative route, comparing with schema documentation, or checking invariants.

\subsection{Metrics}

We report the following metrics:
\begin{itemize}
    \item \textbf{Task Success Rate (TSR):} the fraction of tasks that satisfy the clean reference answer or rubric.
    \item \textbf{Poisoned Degradation ($\Delta$TSR):} the drop from clean TSR to poisoned TSR.
    \item \textbf{Blind Compliance Rate (BCR):} the fraction of poisoned runs in which the agent directly uses the poisoned observation in the final answer or downstream computation without qualification or independent validation.
    \item \textbf{Anomaly Detection Rate (ADR):} the fraction of poisoned runs in which the agent explicitly identifies a discrepancy, implausibility, or possible tool error.
    \item \textbf{Validation Rate (VR):} the fraction of poisoned runs in which the agent performs an independent check, such as recomputing from raw data, querying another tool route, inspecting schema evidence, or comparing against invariants.
    \item \textbf{Recovery Rate (RR):} the fraction of poisoned runs where the agent identifies the issue through anomaly detection or validation evidence and still produces the clean answer or an appropriately qualified final answer.
\end{itemize}

BCR, ADR, VR, and RR are computed over toxic-environment runs. Clean-environment runs are used to estimate baseline task competence and to interpret poisoned degradation. This separation prevents ordinary clean-task failure from being mistaken for trust-calibration failure.
