\section{Discussion and Limitations}
\label{sec:discussion}

\benchmarkname{} targets a narrow but important reliability question: whether tool-using data agents can distinguish a successful tool call from a trustworthy observation. This focus has several implications.

First, not every surprising tool output is wrong. Real datasets contain outliers, schema mistakes, and counterintuitive relationships. A robust agent should not reject observations merely because they are unexpected; it should validate them. For this reason, our metrics distinguish anomaly detection, validation, and recovery.

Second, benchmark poisoning must avoid being unrealistically obvious. If every poisoned observation violates a simple invariant, the benchmark measures only basic sanity checking. We therefore include multiple severity levels and semantic poison cases where the discrepancy requires cross-checking across tools or data sources. The current semantic/schema suite includes biased retrieval evidence and has been run across the same three-model set as the numerical cross-model experiments for the practical-speed adapters. It is still small enough that larger task families and confidence intervals are needed before making fine-grained model-level claims.

Third, poisoning boundaries differ across frameworks. LangGraph, smolagents, \texttt{data2mcp}, and AutoGen expose relatively direct tool-observation boundaries. PandasAI is currently poisoned at a coarser chat-result boundary, and DA-Agent observations may include execution traces. These are realistic end-to-end surfaces, but they are not identical instrumentation points. We therefore report adapter-specific limitations rather than treating every number as a pure model comparison.

Fourth, \methodname{} increases tool-use and routing overhead because it asks the agent to write expectations and perform validation. In the \texttt{data2mcp} ablation, base runs average roughly one dataframe tool event per environment. Full guarded runs average about two to three events, depending on the suite, while light guarded runs remain in the same range but with a tighter turn budget. The light variant keeps observed BCR at zero but loses task success relative to the full guard, so the current implementation favors robustness over latency. Future work should learn when to activate full verification only for high-risk observations.

Finally, the benchmark should be evaluated across more open and closed models, different data-agent architectures, and multiple tool stacks. The main scientific claim should not be that a particular model fails on a particular handcrafted case, but that blind compliance is a measurable and recurring behavior under controlled silent tool unreliability. The current experiments establish this behavior and show that structured guarded verification can reduce it; the next step is broader task scaling, overhead-aware guard activation, and stronger uncertainty estimates for the final tables.
