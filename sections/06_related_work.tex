\section{Related Work}
\label{sec:related}

\paragraph{Tool use and agent reliability.}
Tool-augmented language models learn to call APIs, execute programs, and interleave reasoning with environment actions \citep{schick2023toolformer,yao2023react,gao2023pal}. ToolBench, API-Bank, and Gorilla primarily evaluate tool selection, argument construction, and task completion \citep{qin2023toolllm,li2023apibank,patil2024gorilla}; agent benchmarks further study long-horizon planning and recovery from invalid actions or explicit failures \citep{liu2023agentbench,zhou2023webarena,vuddanti2025paladin}. Trajectory-centered work argues that reliability should be decomposed beyond final success \citep{mazaheri2026agentatlas,vuddanti2026err,kohl2026structural}. ToxicBench addresses a different point in the loop: the correct tool is called and reports success, but its observation is false. The challenge is therefore evidence trust rather than tool selection or exception recovery.

\paragraph{Poisoned external evidence.}
Prompt injection and tool-description attacks place malicious instructions or metadata in content consumed by an agent \citep{perez2022ignore,greshake2023indirect,li2026mcpitp,ye2026trustdesc}. Agent-security studies likewise show that corrupted tool outputs can shift downstream behavior without visible execution errors \citep{li2026agentcanary,wu2026agentdrift,zhang2026agentsentry}. RAG attacks and benchmarks manipulate retrieved corpora or contexts \citep{liang2025saferag,chen2025poisonarena,li2025cparag}. ToxicBench is complementary: it standardizes corruption at the data-agent observation boundary, including plausible aggregates, entity labels, schema meanings, stale metadata, and retrieved evidence. This controlled boundary makes it possible to distinguish copying, anomaly detection, independent validation, and recovery in paired clean/poisoned trajectories.

\paragraph{Data quality and verification defenses.}
Data-validation systems detect schema violations, missing values, and distribution shifts before analysis \citep{schelter2018automating,breck2019data}; RADAR evaluates reasoning over imperfect tables \citep{gu2025radar}. ToxicBench instead preserves the underlying task and silently changes a successful observation, probing whether agents audit evidence after tool execution. Existing defenses filter or constrain evidence using provenance, credibility, attention, runtime policies, or output contracts \citep{dekel2026sdag,jia2025ragrank}. Claim-level systems such as RAGShield extract numerical claims and check them against a cross-source registry \citep{patil2026ragshield}; ToolCritic learns to identify tool-use errors and gives turn-level corrective feedback \citep{hamad2025toolcritic}. These methods address adjacent surfaces, but neither is a drop-in baseline for arbitrary dataframe and schema observations. Guarded Verification instead enforces a fresh evidence-producing action at the observation boundary. It is related to self-refinement and metacognitive verification \citep{shinn2023reflexion,madaan2023selfrefine,zhou2024metarag,zhang2025cosight,ma2025pou}, but targets a specific boundary and evaluates behavior with explicit trust-calibration metrics. Confidence-aware methods could complement this always-on guard by deciding when verification cost is justified \citep{xuan2026confidence,wang2026mirror,subramani2025mice}, while AgentProp-Bench motivates explicit calibration of automated trajectory judgments \citep{gurram2026agentprop}.

\paragraph{Filtering, contracts, and independent evidence.}
These defense families address different failure surfaces. Retrieval filtering and credibility ranking decide which sources enter the context; sanitization isolates instruction-like content; runtime contracts reject outputs that violate known types, ranges, or policies. Proof-of-Use additionally requires that an answer causally use approved evidence \citep{ma2025pou}; this is stronger than provenance-only filtering, but it does not by itself establish that an approved numerical observation is correct. Guarded Verification asks a different question after a successful return: does a fresh computation or inspection support adopting the claim? It is therefore complementary rather than a replacement. A PoU-style contract can enforce use of the verification result, RAGShield-like claim checks can specialize numerical verification, provenance can choose a source-diverse route, and a tool critic can trigger the check. We do not report head-to-head numbers for these systems because their published implementations target different interfaces; ToxicBench provides a paired protocol on which adapted versions can be compared.
