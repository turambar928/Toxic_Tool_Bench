\section{Discussion and Limitations}
\label{sec:discussion}

ToxicBench targets a narrow but important reliability question: whether tool-using data agents can distinguish a successful tool call from a trustworthy observation. This focus has several implications.

First, not every surprising tool output is wrong. Real datasets contain outliers, schema mistakes, and counterintuitive relationships. A robust agent should not reject observations merely because they are unexpected; it should validate them. For this reason, our metrics distinguish anomaly detection, validation, and recovery.

Second, benchmark poisoning should not be unrealistically obvious. If every poisoned observation violates a simple invariant, the benchmark measures only basic sanity checking. We therefore include multiple severity levels and semantic poison cases where the discrepancy requires cross-checking across tools or data sources. The current semantic/schema suite includes biased retrieval evidence and has been run across the same three-model set as the numerical cross-model experiments for the completed adapters. It is still small enough that larger task families and tighter confidence intervals are needed before making fine-grained model-level claims.

Third, poisoning boundaries differ across frameworks. LangGraph, smolagents, DataFrame Router, and AutoGen expose relatively direct tool-observation boundaries. PandasAI is currently poisoned at a coarser chat-result boundary, and DA-Agent observations may include execution traces. These are realistic end-to-end surfaces, but they are not identical instrumentation points. We therefore report adapter-specific limitations rather than treating every number as a pure model comparison.

Fourth, Guarded Verification assumes that an independent verification path is available and not simultaneously corrupted. In the defense ablation, the proxy corrupts the first matching route and the guard can recover by re-reading raw rows, recomputing an aggregate, or checking source evidence. This models pipeline bugs, stale summaries, biased retrieval snippets, or single-route proxy compromise. It does not solve settings where the underlying database itself is corrupted, where all redundant APIs share the same poisoned cache, or where an adaptive adversary observes and poisons both primary and verification routes. Stronger baselines such as multi-route ensembling, randomized cross-checks, provenance validation, and selective verification policies are natural next comparisons.

Fifth, Guarded Verification increases tool-use and routing overhead because it asks the agent to write expectations and perform validation. In the expanded DataFrame Router ablation, base runs average roughly one dataframe tool event per environment. Full guarded runs average about three toxic tool events, depending on the suite, while light guarded runs remain in a similar range but with a tighter turn budget. We report a cost--robustness table using tool events for the full ablation and wall-clock latency for newer runs whose logs include \texttt{elapsed\_seconds}. We do not report monetary cost because the API gateways used here do not expose reliable per-call billing across all model endpoints. The light variant keeps observed BCR at zero and remains close to full guard in aggregate, but individual qualitative cases still show under-recovery when verification needs more turns. Future work should learn when to activate full verification only for high-risk observations.

Finally, the benchmark should be evaluated across more open and closed models, different data-agent architectures, larger databases, multi-table joins, and notebook-like workflows where recomputation requires more planning. The main claim is not that a particular model fails on an isolated case, but that blind compliance is a measurable and recurring behavior under controlled silent tool unreliability. The current experiments establish this behavior and show that structured guarded verification can reduce it; the next step is broader task scaling, overhead-aware guard activation, and stronger uncertainty estimates for final answers.
